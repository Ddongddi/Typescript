# 퀵패치 절차

입력 위치 오류, 글자 유실·중복, 입력 불능, 크래시, 잘못된 업데이트처럼 사용자의 작업을 방해하는 버그를 긴급하게 고칠 때 사용합니다. 기능 추가와 일반 개선은 [기존 릴리스 절차](../CONTRIBUTING.md#변경-기록)를 따릅니다.

퀵패치는 수정 범위와 중복 작업을 줄입니다. 재현 검증, 사용자 데이터 보존, 공식 서명, 배포 CI는 생략하지 않습니다. 사용자가 릴리스를 요청했다면 공개까지 진행하고, 태그 푸시만으로 완료했다고 보고하지 않습니다.

## 1. 범위와 재현

1. `git status --short`, 현재 브랜치, 원격 최신 릴리스·태그를 확인합니다. 사용자 변경은 보존하고, 관련 없는 미배포 변경은 포함하지 않습니다. 필요하면 최신 릴리스에서 별도 패치 브랜치를 만듭니다.
2. 문제가 나는 플랫폼, 입력 순서, 기대 결과와 실제 결과를 기록합니다. 실제 서비스 경로를 통과하는 가장 작은 회귀 테스트를 먼저 실패시킵니다. 입력 버그는 기존 글자와 선택 범위가 보존되는지도 확인합니다.
3. 공통 원인과 호출 경로를 확인한 뒤 필요한 부분만 수정합니다. 리팩터링, 새 의존성, 다른 기능은 섞지 않습니다.

## 2. 배포 전 검증

수정 전 실패한 검증이 수정 후 통과해야 합니다. 같은 경로의 정상 입력과 인접 동작도 확인합니다.

| 수정 범위 | 배포 전 로컬 검증 |
| --- | --- |
| Android 서비스·키보드만 | APK 빌드, `cargo test -p tacit-android`, 에뮬레이터 또는 기기의 `./platforms/android/smoke.ps1 -Serial <serial>` |
| Windows·macOS·Linux 어댑터만 | 해당 플랫폼 빌드와 재현·회귀 검증 |
| 공통 엔진·사전·팩·설정·업데이트 | 관련 통합 검증과 `cargo test --workspace --all-features`; 판별·성능 경로가 바뀌면 기존 정확도·성능 측정도 수행 |

`cargo fmt --all -- --check`와 `cargo clippy --workspace --all-targets -- -D warnings`를 확인합니다. 기존 검증 결과는 코드와 관련 설정이 그대로일 때 재사용합니다. 버전·변경 기록만 고쳤다고 이미 통과한 에뮬레이터 검증을 반복하지 않습니다.

플랫폼에만 한정된 수정은 관련 없는 로컬 전체 빌드·패키징과 엔진 성능 보고서 갱신을 생략합니다. 전체 테스트와 플랫폼 패키징은 기존 릴리스 워크플로가 수행하며, 실패하면 공개 단계에 도달하지 않아야 합니다. 실기기를 사용할 수 없다면 에뮬레이터로 검증하고 실기기 미검증을 결과에 적습니다.

## 3. 버전과 변경 기록

1. 호환 형식이 그대로면 최신 공개 버전의 패치 번호를 하나 올립니다. 예: `0.10.6` → `0.10.7`. 같은 태그를 옮기거나 공개된 파일을 몰래 교체하지 않습니다. 호환성이 깨지는 변경은 일반 릴리스 절차로 전환합니다.
2. 7개 `Cargo.toml`, 루트 `Cargo.lock`, `lab/Cargo.lock`의 해당 로컬 패키지 버전, 두 README의 예시 버전을 맞춥니다. lab 자체 버전은 올리지 않습니다.
3. `CHANGELOG.md`와 `CHANGELOG.en.md`에 버전·날짜·사용자 관점의 수정 내용과 비교 링크를 넣습니다. `sh scripts/release-notes.sh vX.Y.Z`로 공개될 노트를 확인합니다.
4. `git diff --check`와 변경 파일 목록을 확인하고 `git commit -s`로 서명 줄을 포함해 커밋합니다.

## 4. 공식 배포

사용자가 릴리스를 요청한 경우 진행합니다. 버그 수정만 요청했다면 검증된 패치까지 마칩니다.

1. 새 `vX.Y.Z` 태그를 만들고 해당 커밋과 태그를 푸시합니다. `main`에서 배포할 때의 예시는 다음과 같습니다. 별도 패치 브랜치라면 실제 브랜치 이름을 사용합니다.

   ```sh
   git tag vX.Y.Z
   git push --atomic origin main vX.Y.Z
   gh run list --workflow release.yml --limit 5
   ```

2. `.github/workflows/release.yml`의 해당 태그 실행을 추적합니다. 이 워크플로가 공식 키로 APK를 서명하고 테스트·패키징 뒤 릴리스를 공개합니다. 로컬 디버그 서명 APK를 공식 릴리스에 올리지 않습니다.
3. 빌드 중에는 현재 단계를 짧게 알립니다. 실패하면 실패한 로그와 원인을 확인합니다. 일시적인 인프라 오류만 같은 커밋에서 재실행하고, 코드 수정이 필요하면 수정 커밋과 새 버전·태그로 다시 진행합니다.
4. 별도 패치 브랜치에서 배포했다면 수정 내용을 개발 브랜치에도 반영해 다음 릴리스에서 되돌아가지 않게 합니다.

## 5. 공개 확인과 완료

1. `gh run view <run-id>`에서 배포 성공을 확인합니다.
2. `gh release view vX.Y.Z --json tagName,isDraft,isPrerelease,url,assets`로 정식 공개 여부와 대상 파일 존재를 확인합니다. Android 수정이면 `tacit.apk`가 있어야 합니다.
3. `gh release download vX.Y.Z --pattern tacit.apk --dir <새 임시 폴더>`처럼 실제 공개 파일을 내려받아 크기가 0이 아닌지 확인합니다. Android는 SDK의 `apksigner verify --print-certs <apk>`로 서명을 검증하고 직전 공식 APK와 인증서 SHA-256이 같은지 확인합니다. 이 비교는 기존 설치 위에 업데이트할 수 있는지 확인하기 위한 것입니다.
4. 릴리스 링크와 직접 다운로드 링크, 수정 내용, 통과한 검증, 생략한 확인을 짧게 보고합니다. 공개 파일을 확인하기 전에는 “배포 완료”라고 말하지 않습니다.

## 배포 후 문제

입력·데이터 손상이 다시 발견되면 사용자가 승인한 배포 범위에서 후속 패치를 우선합니다. 이전 동작으로 돌릴 때도 현재 버전보다 높은 패치 버전으로 릴리스합니다. 기존 태그·첨부파일을 덮어쓰거나 사용자 사전·설정을 삭제하지 않습니다.
