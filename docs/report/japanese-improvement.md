# 일본어 변환 개선 — 0.9.1 → 0.10.0 개발판

2026-10-18. Mozc와 azooKey의 코드·사전·모델 구조를 비교한 뒤 **Mozc OSS의 사전과 접속 비용을 기존 Rust 변환기에 흡수**했다. Mozc 프로그램을 실행하거나 C++·Swift 런타임을 연결하지 않는다. 선택 근거와 양쪽 소스의 고정 커밋·라이선스·실측 크기는 [비교 조사](japanese-engine-research.md)에 있다. 아래 수치는 완제품 Mozc와 azooKey의 대결 점수가 아니라, **같은 tacit 평가기로 잰 기존 엔진과 수정 엔진의 비교**다.

## 정확도

| 평가 | 건수 | 기존 첫 후보 | 개선 첫 후보 | 기존 Top-5 | 개선 Top-5 |
|---|---:|---:|---:|---:|---:|
| AJIMEE, 왼쪽 문맥 없는 독립 세트 | 100 | 11.00% | **53.00%** | 29.00% | **73.00%** |
| AJIMEE, 원래 문맥이 있는 세트에서 문맥을 제외한 실험 | 100 | 8.00% | **49.00%** | 24.00% | **70.00%** |
| Mozc OSS 정확 일치 회귀 세트 | 220 | 15.45% | **70.00%** | 43.18% | **92.73%** |
| Mozc OSS 정규식 조건 충족률 | 90 | 51.11% | **81.11%** | 해당 없음 | 해당 없음 |
| 직접 작성한 일상·동음이의어·활용·고유명사·외래어·혼합 입력 | 64 | 70.31% | **85.94%** | 93.75% | **96.88%** |

AJIMEE 문맥 없는 세트의 최소 문자 오류율(MinCER)은 **64.58% → 5.21%**, 문맥 제외 세트는 **61.81% → 8.50%**다. 허용 답안이 여러 개면 그중 하나와 정확히 일치해야 문장 정답이고, CER은 각 답안에 대한 Unicode 문자 단위 편집 거리 중 최소값이다. 띄어쓰기·문장부호·표기 차이를 임의로 지우지 않았다. 카타카나 입력만 히라가나로 정규화한다.

자동 판별은 같은 60개 일본어 로마자 입력에 대해 문맥 없음·직전 일본어에서 모두 100%, 별도 영어 보호 20개는 100%를 유지한다. 한자 변환과 언어 판별은 다른 지표다. 이번 변경은 언어 판별 트라이그램 모델을 바꾸지 않는다.

## 흡수한 내용

- Mozc `0136c35782536cb43d710575c311cd4185982738`의 기본 사전 10개, 공식 필터, 보조 사전, 수작업 단어·지명, 2672×2672 접속 비용을 사용한다. 보조 사전의 품사·비용 상속은 해당 커밋의 공식 Python 생성기를 실행해 재현한다. 우편번호 사전·예측·rewriter·사용자 학습 모델 전체를 복제한 것은 아니다.
- 최종 사전은 1,281,710항목·744,378읽기다. 평가 문장을 단어 사전이나 비용 보정에 넣지 않는다. 같은 표면형이어도 문맥 ID가 다르면 남긴다.
- 기존 Viterbi/A* 탐색, 후보 창, 문절 일부 확정, 사용자 선택 학습, 플랫폼 어댑터를 재사용한다. 기존 IPADIC용 절대 비용 임계치를 Mozc 비용에 적용하지 않아 긴 문장이 통째로 가나로 밀리는 문제를 피한다.
- 같은 읽기의 n번째 항목을 찾으려고 앞 항목들을 매번 다시 훑던 경로를 한 번 순회로 바꿨다. 가능한 모든 부분 문자열을 할당·재인코딩하던 작업도 입력당 한 번 인코딩으로 바꿨다. 필요 없어진 항목 개수의 누적 배열 하나를 제거했다.
- `TSIPDIC4`는 12비트 문맥 ID, u16 동음이의어 개수, u32 Unicode 문자를 지원한다. ID 2048 이상·비BMP 한자·잘린 파일·잘못된 문자·개수·오프셋을 테스트한다. 구형 `TSIPDIC3` 읽기는 유지한다.

## 크기와 호환

| 항목 | 기존 | 개선 |
|---|---:|---:|
| 일본어 사전, 압축 전 | 9,696,266 bytes | 38,137,564 bytes |
| 일본어 배포 팩 | 4,877,393 bytes | 14,978,635 bytes |

일본어를 설치할 때만 큰 사전을 받는 기존 선택형 팩 구조를 유지한다. 배포 팩에는 Mozc 원문 라이선스·사전 고지·입력별 SHA-256·출처 커밋도 들어간다. 사전 데이터의 라이선스는 프로젝트 코드의 AGPL과 구분한다.

새 팩을 0.9 프로그램이 읽을 수 없으므로 개발 버전을 **0.10.0**, 팩 호환 범위를 `>=0.10.0, <0.11.0`으로 올렸다. 기존 0.9 팩을 새 개발판에서 쓰려면 프로그램과 팩을 함께 갱신해야 한다.

## 지연·메모리와 검증

같은 Windows PC, rustc 1.93.1, lab 0.1.2에서 구·신 바이너리를 순서를 뒤집어가며 5회씩 실행했다. 각 실행의 통계량을 구한 뒤 그 중앙값이다. 외부 평가의 서로 다른 읽기 506개를 한 번씩 변환하며, 최장 117가나 문장도 제외하지 않았다. 빌드·테스트 프로세스가 끝난 뒤 측정했다. [원시 통계·고정 데이터 해시·바이너리 해시](japanese-metrics.json)를 보존했다.

| 지표 | 기존 | 개선 |
|---|---:|---:|
| 외부 세트 변환 평균 | 332.6µs | 429.3µs |
| 외부 세트 변환 p50 | 190.9µs | 279.7µs |
| 외부 세트 변환 p95 | 1382.9µs | 1419.1µs |
| 외부 세트 변환 p99 | 1939.9µs | 2175.5µs |
| 자체 64건 변환 평균 | 127.6µs | 217.2µs |
| 자체 64건 변환 p95 | 229.3µs | 387.8µs |
| 최초 사전 초기화 | 14.1ms | 50.1ms |
| 일본어 lab 프로세스 최대 working set | 19,940KiB | 43,480KiB |

**정확도와 맞바꾼 비용이 있다.** 외부 세트 평균 지연은 약 29%, p99는 약 12% 늘었고, 최초 초기화와 배포 크기도 증가했다. 속도가 빨라졌다고 주장하지 않는다. 새 인덱스의 초기화 직후 힙 증가는 5816.6KiB이며, 여기에 읽기 전용 사전 페이지가 별도로 매핑된다. 기존 바이너리에는 동일한 일본어 힙 지표가 없어 이전 값을 추정해 채우지 않았다.

최대 working set은 임베디드 사전을 담은 lab 실행 파일을 별도로 5회씩 실행하고 Windows `GetProcessMemoryInfo`의 `PeakWorkingSetSize`를 1ms마다 조회한 관측 중앙값이다. 실제 앱에 로드된 TIP의 메모리 수치가 아니며, 배포판의 mmap 공유 효과와 같다고 해석하지 않는다.

### 0.10.1 후속 최적화

0.10.0 직후 후보 탐색과 사전 불러오기만 고쳤고, 사전 형식·팩·출력은 그대로다(외부 506개 읽기에서 바이트 단위로 같다). 같은 PC에서 0.10.0 바이너리와 0.10.1 바이너리를 7회 번갈아 실행해 각 쌍의 비율을 평균했다. 이 PC는 측정 당시 부하가 커서 절대 시간은 위 표보다 느리게 나왔으므로 **비율만** 기록한다.

| 지표 | 0.10.1 / 0.10.0 |
|---|---:|
| 외부 세트 변환 평균 | 0.54 |
| 외부 세트 변환 p50 | 0.58 |
| 외부 세트 변환 p95 | 0.50 |
| 외부 세트 변환 p99 | 0.51 |

| 지표 | 0.10.0 | 0.10.1 |
|---|---:|---:|
| 최초 사전 초기화 | 약 45ms | 약 4ms |
| 초기화 직후 힙 증가 | 5816.6KiB | 2999.7KiB |

변환기 단계별 시간(평균 17가나·노드 685개)은 격자 구성 141µs, Viterbi 138µs, N-best 488µs였고, 병목이던 N-best가 줄었다. 사전 접두어 탐색 범위 축소만의 효과는 약 3%였다. 정확도는 바꾸지 않았다.

검증: 워크스페이스 **421개 통과·0개 실패·1개 기본 제외**, 일본어 lab 테스트 2개 통과, 포맷·Clippy·워크플로 Prettier 통과, Windows x86 릴리스 빌드 통과. 기본 제외 테스트는 시스템 입력기를 실제로 바꾸는 검사다. 새 팩 카탈로그의 버전·호환 범위·각 파일 해시와 라이선스 동봉을 확인했고, 고정 소스에서 다시 만든 사전 및 출처 JSON은 바이트 단위로 일치했다. 사전 SHA-256은 `61b1577892897a9c0a45674dae28a7eb67463d52f2c45312656be9728f576b5b`다.

실제 앱 설치와 macOS·Linux·Android 장치에서의 입력은 이 작업에서 실행하지 않았다. CI에 일본어 품질 하한을 추가했지만, 변경을 푸시하지 않았으므로 원격 CI 실행 결과로 표현하지 않는다.

## 재현

```powershell
# 고정된 원본 소스를 받아 사전을 다시 생성
git clone https://github.com/google/mozc.git temp/mozc
git -C temp/mozc checkout 0136c35782536cb43d710575c311cd4185982738
python tools/build_mozc.py --source temp/mozc/src/data/dictionary_oss
python tools/build_mozc.py --selftest

# 자체 평가와 외부 평가; raw 데이터는 lab/data/japanese/에만 캐시
cargo test --manifest-path lab/Cargo.toml japanese
cargo run --release --manifest-path lab/Cargo.toml -- --japanese
python lab/evaluate_japanese.py --selftest
python lab/evaluate_japanese.py --check --out temp/japanese-evaluation.json

# 기존 입력 경로와 팩 설치를 함께 검증
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release -p tacit-tip --target i686-pc-windows-msvc
```

Linux/macOS에서는 `--binary lab/target/release/tacit-lab`를 평가 명령에 붙인다. CI의 `japanese` 작업은 자체 평가와 외부 평가의 품질 하한을 검사한다. 단위 테스트만 통과하고 실제 문장 점수가 무너지는 변경을 허용하지 않는다.

## 평가 출처와 한계

- [AJIMEE-Bench JWTD_v2/v1](https://github.com/azooKey/AJIMEE-Bench/tree/401666cd56d1a570c2021798b64b6da4396bfd45): 일본어 Wikipedia 입력 오류 데이터셋 v2의 테스트 자료에서 추출·수작업 확인한 200건, CC-BY-SA 3.0. Mozc 사전과 별개로 선택한 독립 자료다. 원래 왼쪽 문맥이 있는 100건에는 현재 변환기에 전달할 문맥 인터페이스가 없어 문맥을 생략했다고 명시했다.
- [Mozc OSS 회귀 데이터](https://github.com/google/mozc/blob/0136c35782536cb43d710575c311cd4185982738/src/data/test/quality_regression_test/oss.tsv): 같은 소스 계열의 회귀 자료이므로 독립 정확도 증거로만 쓰지 않는다. `Conversion Match/Not Match`는 전체 문자열 정규식으로 검사한다. Mozc의 문절별 N-best 순위와 달라지는 `Expected 2/9/99` 등은 공식 점수인 것처럼 합산하지 않는다.
- 직접 작성한 64건은 개발용 회귀 자료이며 대표 인구의 실사용 정확도 추정치가 아니다. 일본어 골든 스냅샷의 후보 순서·실시간 표시 변경은 의도된 데이터 변경으로 갱신했고, 영어·한국어 판별 스냅샷은 바꾸지 않는다.
- 남은 오류는 동음이의어, 숫자·고유명사, 외부 문맥이 필요한 표기, 지원되지 않는 읽기의 어색한 후보 등이다. 전체 Mozc의 예측·교정·rewrite나 azooKey Zenzai의 신경망 문맥 추론과 동등하다고 주장하지 않는다.
