## 1. 캐스케이드 재점수: 채택 안 함

제안 구조는 기존 엔진 위에서 확신이 낮은 토큰만 1순위·2순위 언어 중에서 로지스틱 헤드로 다시 고르고, 문맥 n-gram 팩(약 1MB)을 새로 두는 것이었다. 안 한 이유:

- `viterk`의 runner_up은 `korean`이고 정답은 `mixed`(vite가)다. 재점수는 후보 안에서만 고르므로 정답에 닿지 못한다.
- 문장 첫 동형어(`so`→내, `Eh`→또)에는 왼쪽 문맥이 없다. 단서는 뒤에 오는 단어뿐이다.
- 엔진 힙은 35KB뿐이고 메모리는 mmap하는 팩(en 1.58MB 텍스트, ko 약 1.1MB)이다. 1MB 팩을 더하면 "메모리를 줄인다"와 반대다.
- 살린 것: 신뢰도 보정, 상한부터 재고 작으면 멈추는 규칙, 키 상한, 안전 규칙.

## 2. 한국어 LM: 건너뜀

남은 오류가 한국어 음절 점수 때문이라는 가정을 검증했다.

- `big.ko.title.after-en` 오답 59개를 맥락 없이(`--decide`) 다시 넣으면 **55개가 맞다**. 원인은 점수가 아니라 "앞 단어가 영어"라는 사전 확률이고, 이 버킷은 임의의 영어 뒤에 임의의 위키 제목을 붙인 합성이다.
- 사전에 없는 음절(tier 표·코퍼스 표 어디에도 없음)은 오답 59개의 음절 174개 중 8개.
- NSMC 원본에는 `ㅋㅋ` 4177, `ㅁㅊ` 26, `ㄴㄴ` 20회처럼 줄임말이 드물다. 기존 `lab/data`는 `[가-힣]`만 통과시켜 자모 토큰이 0이다. `ac`→ㅁㅊ는 영어 `ac`와의 사전 확률 문제라 말뭉치만으로 안 풀린다.
- 문장 세트 오답을 토큰으로 나눈 분포(`--misses 80` 표본): 짧은 동형어 115, 기타 133(Shift 자음 한글↔영어 대문자 55 포함), 영어 용어+조사 17, `-` 포함 6, 숫자 2.

## 3. 오른쪽 문맥 재판단: 채택

불확실한 단어(confidence < 0.8) 뒤에 같은 줄에서 확신 있는 다른 언어 단어(≥ 0.95)가 오면, 그 언어를 앞 단어 언어로 준 것처럼 다시 판단한다. 처음엔 `lab`에서만 시험(`LAB_LOOKAHEAD`)하고, 효과가 확인된 뒤 코어 `TextConverter`로 옮겼다(`without_look_ahead()`로 끌 수 있음).

| 지표 | 끔 | 켬 |
| --- | --- | --- |
| `sc.chat.slang` | 82.35 | 88.24 |
| `sc.chat.sentence` | 95.35 | 96.51 |
| `big.ko.sent.sentence` | 97.93 | 98.40 |
| `big.ko.long.sentence` | 96.40 | 97.00 |
| `big.cs.bare.sentence` | 96.00 | 96.59 |
| `big.cs_heldout.particle.sentence` | 96.37 | 96.96 |
| `sc.ALL.sentence` | 97.74 | 98.12 |

`big.en.sent`, `sc.dev`, `sc.writing`, `acc.ALL`은 변화 없음. 임계값은 0.7/0.9, 0.8/0.95, 0.9/0.95, 0.97/0.98을 시험해 0.8/0.95에서 평탄(0.6/0.9는 채팅 지표가 안 오름). 임계값을 이 세트에서 골랐으므로 수치는 낙관적이다.

주의: 라이브 입력기에는 **적용하지 않았다**. 이미 화면에 확정된 앞 단어를 뒤집는 UX라 별도 결정이 필요하다. CLI 변환과 테스트 경로에만 적용된다.

## 4. 기술 이름 트라이그램: 폐기

`nodejs`·`sonarqube`·`viterk` 같은 사전 밖 영어 용어를 겨냥해, PyPI 다운로드 상위 15,000개 패키지 이름을 토큰으로 쪼갠(10,942개) 두 번째 문자 트라이그램 표를 기존 표와 섞어 보았다. 홀드아웃 오염을 막으려고 `terms.txt`의 모든 용어를 학습에서 뺐다(213개 중 139개가 PyPI 이름에 그대로 있었다).

| 지표 | 혼합 0 | 0.2 | 0.4 |
| --- | --- | --- | --- |
| `big.cs_heldout.particle.sentence` | 96.96 | 96.61 | 97.08 |
| `big.cs.bare.sentence` | 96.59 | 96.36 | 96.12 |
| `big.ko.sent.sentence` | 98.40 | 98.30 | 98.13 |
| `big.ko.long.sentence` | 97.00 | 96.80 | 96.60 |

이유: `nodejs`는 `nod`+`던의`가 gap 15.2점으로 이기고 있어서 철자 확률 몇 점으로는 못 뒤집는다. 필요한 건 철자 패턴이 아니라 "nodejs라는 단어를 안다"는 어휘 정보인데, 홀드아웃 용어를 어휘 목록에 넣으면 그 지표가 재려는 일반화가 사라진다. 코드와 표는 남기지 않았다.

## 5. `-` 하드 제약: 보류

- `viterk`는 분할(`vite가`)은 맞지만 gap 0.84가 `margin` 1.0에 못 미쳐 버려진다. `sonarqube가`는 gap −0.93. `Wi-Fieh`는 `analyze`가 영문자 이외 키가 있으면 바로 `None`을 돌려준다.
- `CodeSwitch::analyze`가 `Wi-Fieh`를 `WiFieh`로 풀어 자르고 `-`를 영어 구간에만 되돌려 넣도록 했다(`Wi-Fi도`, `e-mail를`, `안녕-hello`, 한국어 구간 안의 `-`는 컷 폐기). 단위 테스트 있음.
- **문장 지표는 변하지 않았다.** `TextConverter`와 라이브 세션이 모두 `-`에서 단어를 끝내므로 엔진에 `Wi-Fieh`가 한 토큰으로 오지 않는다. 문장에서 고치려면 글자 사이의 `-`를 단어 안으로 보는 경계 규칙이 필요한데, 미리보기 밑줄과 확정 시점이 바뀌어서 사용자 결정 전에는 하지 않았다.
- 구현 중 실수 하나: 한국어→영어 경계의 `-`를 두 번 넣어 `안녕--hello`가 나왔다. 경계 케이스 테스트로 잡았다.

## 6. 모양 단위 Esc 학습: 채택(1차)

Esc 교정을 단어 하나가 아니라 그 단어의 **모양**의 증거로 센다. 모양은 `jamo`(초성만 3키 이하), `capital`, `ending`(영어 어간+조사), `short`·`medium`·`long`. `lexicon.json`의 `shapes`에 `"jamo:korean": 3`처럼 서로 다른 키가 몇 개 그 언어로 교정됐는지를 저장한다(없으면 빈 값, 옛 파일 그대로 읽힘). 안쪽 엔진의 margin이 `증거 수 × 0.4`(최대 1.6)보다 작을 때만 영어↔한국어로 뒤집는다. 확신하는 판단과 `Mixed` 판단은 건드리지 않는다.

평가를 위해 `lab`에 `big.transfer.*`를 추가했다: 용어(또는 키) 단위로 절반을 Esc 두 번으로 가르치고, **가르치지 않은 나머지**에서 고쳐진 비율(`fixed`)과, 정답이던 항목 + 영어 대조군이 망가진 비율(`broken`)을 센다. 같은 용어의 다른 조사형은 세지 않는다(기존 어간 학습이 하던 일이라 일반화가 아님).

| 세트 | 기준선 fixed / broken | 지금 fixed / broken | 비고 |
| --- | --- | --- | --- |
| `jamo` | 0% / 0% | **100% / 0%** | 오답 5개 중 3개를 가르치고 2개가 따라옴 |
| `title_after_en` | 0% / 0% | **44.8% / 0.02%** | 13개 고침, 영어 대조군 1개 망침, 순이득 +12 |
| `particle` | 0% / 0% | 0% / 0% | 오답이 확신하는 영어이거나 확신하는 `Mixed`라 안전 한도 밖 |

- `Mixed`로의 뒤집기도 처음엔 넣었는데 `particle`에서 고친 것 0개에 대조군 1개를 망가뜨려서 뺐다.
- 학습한 게 없는 사용자는 동작이 같다. 교정을 한 번이라도 한 사용자부터 적용된다.
- 한계: 모양 증거는 `forget_all`로만 지워진다(단어별 `forget`은 안 지움). 이전 언어를 모양에 넣지 않았다(세션 배선 필요). 대시보드에 안 보인다. 감쇠 없음. 되돌림을 부정 증거로 쓰지 않는다.

## 7. 증거 없는 한국어 꼬리 벌점: 채택

`nodejsdml`이 `nod`+`던의`로 나오는 원인을 추적했다. `던의`는 단어 목록에도 어미 목록에도 없지만, `korean_score`가 "끝에 오는 한국어 꼬리가 2음절 이상이면 증거 없이도 허용"하기 때문에 `nodejs`+`의`와 점수가 비슷해져서 졌다. 이 허용은 목록에 없는 새 한국어 단어(메신저류)를 위한 것이라 없앨 수는 없다. 그래서 단어도 어미도 아닌 꼬리에 벌점(`Params.bare_tail`)을 주는 항 하나를 더했다. 규칙이 아니라 점수 항이고, 튜너(`--tune`)의 좌표 목록에도 넣었다.

같은 표본에서 `bare_tail` 0 / −2 / −4 / −6:

| 지표 | 0 | −2 | −4 | −6 |
| --- | --- | --- | --- | --- |
| `big.cs.particle.sentence` | 96.73 | 96.73 | 97.31 | 97.31 |
| `big.cs_heldout.particle.sentence` | 96.96 | 96.96 | 97.66 | 97.66 |
| `big.cs.bare.sentence` | 96.59 | 96.71 | 96.71 | 96.71 |
| `big.ko.sent.sentence` | 98.40 | 98.43 | 98.43 | 98.43 |

−4부터 평탄해서 −4로 정했다. 전체 지표 중 내려간 것은 없고, `acc.cs.hada` 88.9 → 100, `big.learn.other_forms` 99.28 → 99.84도 올랐다. `nodejs의`·`nodejs에서`·`nodejs했어`를 코드 테스트에 넣었다. 임계값을 이 세트에서 골랐다는 점은 앞과 같다(`terms.txt` 용어는 튜너에도 쓰인다). 남은 `viterk`·`sonarqube`는 이 꼬리 문제가 아니라 영어 쪽이 확신하는 경우다.

실수 하나: 튜너의 필드 배열 길이를 올리지 않아 lab이 컴파일되지 않았고, 그 빈 출력을 "변경 없음"으로 읽을 뻔했다. 비교 전에 두 쪽의 지표 개수가 같은지(107개) 확인해야 한다.

## 8. 사전에 없는 영어 앞부분 벌점: 폐기

계기: 0.8.6 → 0.8.7 비교에서 `acc.en.freq/none`이 99.60 → 99.50. 같은 데이터·같은 lab으로 커밋별로 재서 `46d74a1`(영어+한국어를 한 번의 점수로 나누는 변경)부터임을 확인했습니다. 틀린 단어는 `chandi`→`chan야`, `fatso`→`fat내` 둘입니다. 둘 다 단어 사전에 없고(`fatso`는 빈도 목록에만 있음), `chan`·`fat`은 사전에 있어서 `앞부분 + 한 음절 어미`가 이깁니다.

### 가설과 구현

영어 원문·전체 한글 조합·기존 혼합어 최상위 경로·기존 엔진 출력을 최대 네 개의
후보로 모아 같은 선형 softmax 선택기로 비교했다. 24개 수치 특징 × 3개 언어의
72개 가중치다. 단어 식별자나 평가 정답을 특징으로 쓰지 않는다.
기존 사전·전이 제약·기존 엔진 출력은 후보와 특징에 남아 있다.
혼합어는 N-best 전체가 아니며, 정답 후보를 주입하지 않고 미도달도 집계한다.
모델당 6 epoch, AdaGrad, 같은 난수 시드로 고정했다. 단어 예외·판별 임계값은 추가하지 않았다.

## 19. 전환 점수·진단 문자열의 임시 할당 제거 — 2026-10-19, 20번과 합쳐 채택

측정기 자체의 atomic 계수 비용이 있으므로 예전 lab 시간과 연결하지 않는다.
기존 0/3 개발 정확도/미리보기, 실제 세션, enkoja 가드와 반복 실행 지연·heap·같은 빌드 실행 파일 크기를 확인한다.

기준/후보 순서를 번갈아 7쌍을 실행했다. 종료 시 원래 affinity로 복구했다.
전역 CPU 설정이나 설치된 입력기는 바꾸지 않았다. 다음은 실행별 지표의 중앙값이다.

| 영·한·일 지표 | 최초 기준 | 19+20 | 변화 |
| --- | ---: | ---: | ---: |
| 확정 평균 µs | 67.79 | 64.38 | −5.03% |
| 확정 p95 µs | 149.40 | 145.90 | −2.34% |
| 확정 p99 µs | 223.70 | 219.60 | −1.83% |
| 입력 중 평균 µs | 31.67 | 30.19 | −4.67% |
| 입력 중 p95 µs | 94.20 | 88.80 | −5.73% |
| 입력 중 p99 µs | 155.80 | 147.20 | −5.52% |
| 확정 요청 바이트/판별 | 4603.10 | 4401.60 | −4.38% |
| 입력 중 요청 바이트/판별 | 2081.18 | 1906.74 | −8.38% |
| 로드 heap KiB | 2468.14 | 2468.14 | 동일 |
| lab 피크 heap KiB | 14047.71 | 14047.71 | 동일 |

쌍별 비율의 중앙값은 확정 평균 −1.09%, 입력 중 평균 −4.55%다.
확정 p99는 쌍별 비율 중앙값 +0.18%이고 7쌍 중 3쌍만 빨랐다. 따라서 일본어 확정 p99의
개선은 주장하지 않으며 작은 차이의 우열은 미확정이다. CPU를 고정하지 않은 +3% 결과도 위에 남겼다.
이 검증은 모든 기계·입력의 지연 무회귀를 증명하지 않는다. 판별 동작 보존, 일관된 할당 감소,
같은 heap, DLL 축소 및 최종 평균 지연 결과에 근거하여 19+20을 코드에 유지한다.

## 측정에서 배운 것

- 대조군이 없는 `broken`은 쓸모없다. `title_after_en`은 정답이 전부 한국어라서 영어가 잘못 뒤집히는 부작용이 처음엔 보이지 않았다.
- 지연(`keystroke.avg_us`)은 이 기계에서 잡음이 크다(같은 코드가 13~43µs로 흔들림). 변경 전후를 비교할 땐 같은 실행 안에서 켜고 끄는 방식이 필요하다. 기능이 꺼진 경로의 비용은 잠금 한 번과 빈 맵 복제로 한정했다.
- `lab/baseline.tsv`의 저장값은 다른 표본 크기라 현재 실행과 직접 비교하면 안 된다. 새 지표 행은 아직 baseline에 저장하지 않았다.
- Windows에서 `python -I`는 `PYTHONIOENCODING`을 무시한다. 한글 출력은 파일에 `encoding='utf-8'`로 쓰고 읽는다.
- `rustfmt <파일>`은 그 파일이 선언한 모듈(`lab/src/main.rs` → `tune.rs`)까지 같이 고친다. 의도하지 않은 파일이 바뀌지 않는지 확인할 것.
- 이전 버전과 비교하는 표는 같은 lab(세트·데이터)으로 다시 재야 합니다. 예전 보고서의 값과 새 값을 이어 붙이면 없는 하락이 생기고 있는 상승이 가려집니다(`big.learn.other_forms` 87.5 → 99.84는 세트가 달랐고, 같은 세트에서는 둘 다 100).
